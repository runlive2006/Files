# 性能基线（M1 Sprint 1 实测）

- 日期：2026-10-21
- 对应任务：DEV-PLAN M1 的 1.1 / 1.4 / 1.5 / 1.14
- 结论一句话：**数据层不是瓶颈**。10 万项目录的"枚举 + 映射 + 排序"只要 **131ms**，
  仅占 PRD §5.1「进入目录首屏 ≤600ms」预算的 22%。剩余风险全部在 WPF 视图实现，不在 IO。

---

## 1. 测试环境

| 项 | 值 |
| --- | --- |
| OS | Microsoft Windows 10.0.26300 |
| 运行时 | .NET 10.0.0（Release） |
| 进程架构 | x64 |
| CPU 逻辑核数 | 20 |

| 存储 | 本地 SSD（`D:\Dev\Projects\Files\.dotnet\tmp`） |

> 数据由 `bench/Files.Bench` 生成，测量的是**真实文件系统**，不是内存里的假数据。

## 3. 结论与解读

### 3.1 好消息：IO 与枚举层远超需求

- 一次 `FindFirstFileExW` 循环就拿到名称、属性、大小、修改时间，**零额外 stat**；
- 相比 `Directory.EnumerateFileSystemEntries` 只慢约 17ms（50k）/ 17ms（100k），
  但后者**不提供属性**，要用属性就得再逐项 `FileInfo`（那才是真正的性能杀手）；
- 按 PRD 预算，10 万项首屏 600ms 中，数据层只花 131ms，**剩 470ms 留给 WPF 视图实例化**。

### 3.2 新发现：真正的下一个瓶颈是**每项内存**，不是速度

`Win32DirectoryLister.List` 在 10 万项时分配 **42.69 MB**，折算 **≈ 427 字节/项**：

| 组成 | 估算 |
| --- | --- |
| `FileSystemEntry` 对象头 + 5 个字段 | ~56 B |
| 3 个字符串（`Name`、`FullPath`、派生 `Extension`） | ~120–200 B |
| `List<FileSystemEntry>` 槽位与增长冗余 | ~16 B |
| 排序过程与临时对象 | 其余 |

影响：

- 单栏 1000 项 → 约 0.4MB，**完全在 PRD 预算内**（≤90MB）；
- 但 10 万项目录 → 约 42MB 托管堆，叠加四栏 × 多标签（PRD §5.1 的四栏 ≤150MB、
  四栏×5标签 ≤220MB）会明显吃紧；
- 因此 **PRD §4.2 的"非活动标签只留状态、不留视图"是必须执行的硬约束**，
  否则 4 栏各开一个 10 万项目录就会直接击穿预算。

### 3.3 内存优化（已完成，见第 5 节复测）

基线测得每项约 427 字节后做了三项改动：

| 优化 | 做法 |
| --- | --- |
| `FileSystemEntry` 由 `class` 改 `readonly struct` | 去掉每项的对象头与引用间接层 |
| 不再逐项保存 `FullPath` | 路径提升到 `DirectoryListing.DirectoryPath`，需要时 `GetFullPath` 现拼，省掉每项一个约 100 字符的字符串 |
| 排序键预计算 | `EntrySorter` 对"类型"排序先一次性算扩展名，避免 O(n log n) 次字符串分配 |

### 3.4 尚未优化的项

| 优化 | 预期收益 | 说明 |
| --- | --- | --- |
| 扩展名池化共享 | 小 | `Extension` 是现算属性，不常驻内存，收益有限 |
| 超大目录分段（>10 万项） | 中 | 仅极端场景需要，M3 后评估 |

## 4. 复现方式

```powershell
# 5 万项，含预算判定（超预算退出码 1）
.\scripts\bench.ps1 -Count 50000 -Gate

# 10 万项，保留数据以便复跑
.\scripts\bench.ps1 -Count 100000 -Keep
```

或直接：

```powershell
dotnet run -c Release --project bench/Files.Bench -- --count 100000 --gate
```

> 必须用 `-c Release`。Debug 下的数值受未优化代码与边界检查影响，不能作为验收依据。

---

## 5. 内存优化后复测（2026-10-21）

改动：`FileSystemEntry` 改 `readonly struct`、去掉逐项 `FullPath`、排序键预计算。
测量条件同第 1 节（Release / x64 / 10 万项）。

| 指标 | 优化前 | 优化后 | 变化 |
| --- | --- | --- | --- |
| `Win32DirectoryLister.List` 耗时 | 131.1ms | 144.9ms | +10.5%（噪声范围内，见下） |
| `List` 分配 | 42.69 MB | **23.61 MB** | **−44.7%** |
| 每项分配 | ≈427 B | **≈248 B** | **−42%** |
| 工作集增量 | 34.1 MB | **14.4 MB** | **−58%** |
| `ReadAll` 耗时 | 55.8ms | 69.3ms | +24% |
| `ReadAll` 分配 | 19.79 MB | 19.80 MB | 持平 |

### 5.1 关于耗时"变慢"的说明

`ReadAll` 与 `List` 的耗时上升约 10–24%，**不是优化导致的退化**：

- `ReadAll` 的代码路径完全没有改动（分配也一模一样，19.79 → 19.80 MB）；
- 同一次运行里，未改动的基线 `Directory.EnumerateFileSystemEntries` 也从 38.8ms 涨到 42.3ms（+9%）；
- 这说明本轮测量时机器负载更高（基准台前刚跑完 10 万文件生成）。

结论：**内存指标是可信的，耗时差异属于测量噪声**。后续应把基准台接入 CI 并固定
机器状态，或改用多轮取中位数 + 离散度校验，才能用于耗时回归门禁。

### 5.2 结论

每项 248 字节意味着：

| 场景 | 估算托管堆 |
| --- | --- |
| 单栏 1,000 项 | 0.25 MB |
| 四栏各 1,000 项 | 1.0 MB |
| 单栏 100,000 项 | 24.8 MB |
| 四栏各 100,000 项 | 99 MB（**超出 150MB 预算的可控范围，必须靠"非活动标签不留视图"约束**） |

这组数字直接支撑 PRD §4.2 的硬约束：**标签是状态容器，不是预创建的视图**。
